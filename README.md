# Loco hiring!

Do you want to hire employees? Do not go Loco! 

LocoHiring is a simple solution to help recruiters, candidates and interviewers to get all the hiring process under 
control. It provides a website so that 

1. Recruiters can keep track of the candidates on different hiring funnels
2. Interviewers can declare their availability for interviewing and have a single place to know get information about 
the candidate, its resume and interviewing history
3. Interviewers can provide written feedback, the feedback is available for other interviewers and recruiters to see
4. The whole history of a candidate, its interviews, feedback and outcome is stored in a single place

LocoHiring is a simple solution that is composed of 4 components, each component maps to a different java maven project.
All the projects are under a single git repository to simplify the process of building them. 

1. LocoHiringDB: A liquibase project in charge of defining the DDL and DML required to start up the project.
2. LocoHiringService: A REST based API which allows to interact with the database, apply business rules, etc.
3. LocoHiringJavaClient: A java client used to connect to the LocoHiringService.
4. LocoHiringWeb: A server side rendered website using Thymeleaf as a rendering engine.

First lets describe how everything works. 

Recruiters will define a hiring funnel. A funnel is composed of a set of interview types, different candidates will 
go through the same hiring funnel, for example a hiring funnel could be named "Software Engineer" and be composed of 
3 interviews: Phone Screen + Coding Interview + Design Interview, another hiring funnel could be "Software manager" and 
it might be composed of 4 Interviews: Phone Screen + Design Interview + People Manager Interview + Behavioural
Interview. 

Hiring funnels are defined by recruiters. 

Then we have the interviewers, these are different people from the recruiters and they need to provide availability for 
interviewing, this is done by having a CalendarAvailability, essentially an interviewer blocks chunks hours in different
days, for example an interviewer might block 1-2pm, 4-5pm on Tuesdays and 9-11am on Fridays for 
interviewing. This allows recruiters to allocate different interviews to different CalendarAvailabilities. 

Once every interview is done, feedback must be written. This is the job of the interviewer who performed the interview.
An interview may have more than one interviewer (sometimes one interviewer + 1 shadow), whoever interviewed a candidate 
must enter feedback. The feedback includes a yes/no (interviewer is inclined to proceed with the candidate or not) and 
several notes about it (a text).

Every candidate that goes through a funnel must ultimately get a yes/no response, meaning whether he is hired or not 
hired. 

## LocoHiringDB

To perform all of this, i have come up with the following entities (tables) for a database. I would suggest to use 
PostgreSQL as the database for this. Each Table will have an "id" field which is a number acting as the primary key 
(pk) of the table. These numbers are unique for table and are autogenerated upon insertion. When a table needs a 
reference to another table id (foreign key, fk) I will use the format <other_table_name>_id, for example a field 
named candidate_id refers to the id field on the candidates table (note that tables use plural names, but fields will
always be in singular)

Here is the list of the tables

1. Candidates
    * id
    * email
    * resume (blob)
    * position_id
    * first_name
    * surname

2. Recruiters
    * id
    * email
    * is_admin (boolean)
    * password (bcrypt)
    * first_name
    * surname
    
3. Interviewers
    * id
    * email
    * bar_raiser (boolean)
    * level
    * is_admin (boolean)
    * first_name
    * password (bcrypt)
    * surname
    
4. Interviews
    * id
    * application_id
    * interviewer_id
    * shadow_id (refers to another interviewer_id, might be null)
    * interviewtype_id
    * calendar_availability_id
    * status (enum: LOOKING_FOR_INTERVIEWER, SCHEDULED, COMPLETED, CANCELLED)
    * scheduled_at (timestamp)

5. InterviewFeedback
    * id
    * interview_id
    * interviewer_id
    * feedback (text)
    * inclined (boolean)
    
6. Debriefs
    * id
    * application_id
    * notes
    * inclined (boolean)  
    * scheduled_at (timestamp)  
    
7. InterviewTypes
    * id
    * name
    * description
    
8. Funnels

9. FunnelDetails

10. CalendarAvailability
    * id
    * interviewer_id
    * interview_id
    * date (no hours or minutes!)

11. Positions
    * id
    * level
    * name
    * description
    * jobfamily_id    
    
12. JobFamilies
    * id
    * name
    
13. Interviewers_JobFamily
    * id

14. Events
    * id
    * funnel_id

15. Applications

    * candidate_id

## LocoHiringService

Now lets talk about the LocoHiringService. This will be written in Java21 + SpringBoot + SpringDI + SpringJDBC. I do 
not want ORMs like Hibernate or JPA, instead write the SQL queries in the code. I want every single API available as 
an openapi spec, I will also want a Swagger website for the APIs (and this must be available without having to login). 

AuthN and AuthZ will be done with JWT tokens (with refresh) with 5 minutes expiry. We will use the Recruiters and 
Interviewers table to determine whether the username and password provided by users is correct or not. The email is 
what represents the username here. 

In terms of Authorization here is how it works. 

* Recruiters: They are the only ones to create funnels, interviews, candidates, positions, job families and debriefs. 
Normally a single funnel will hold multiple candidates. In practise we can expect to have 5-20 funnels tops, because 
normally a funnel is designed for a job family, for example we could have funnels for "Software Engineer" another one 
for "Marketing Manager", etc. Notice however that Funnels are not strictly linked to job families, this is because 
we expect that there will be certain level of experimentation with Funnels, so we do not want a strict association.

* Interviewers: Their job is to provide CalendarAvailability and enter feedback for interviews, nothing else. 

* Admin: Can do anything.

About reading data: Only the recruiters and interviewers who are associated with a candidate can see the candidate 
details, this includes not only the data in the candidates table but also the interview, interview feedback, debrief, 
events, etc. The idea is to work on a restrictive approach so that personal data of candidates is not exposed unless 
required. 

When it comes to feedback viewing, interviewers can only see feedback provided by other interviewers about the same 
candidate in the same funnel once they had written their own feedback. Remember that a funnel might be composed of 
multiple interviews. The rationale for this rule is that as an interviewer I should not be biased by the feedback 
of others. Instead I should provide my feedback based solely on the data I collected during the interview I conducted.

Interviews are created by recruiters and might not have an interviewer associated initially, there are different status 
for the interview (see database table). Once a recruiter has created an interview and assigned a time to it, it is his 
job to find an interviewer who can do the interview at the desired time. The time of the interview can be changed 
by the recruiter if required. Interviewers can be reassigned to other interviews if required. 

There is a table of events where we store all the things that occured in the service. This is for auditing purposes, 
every time we create or modify some value, we will store the information in the events table. This gives us good 
diagnoses for what has happened to a candidate in his funnel. 

The structure of the service when writting it in Spring should be like this

* Controllers: These are the HTTP endpoints, they should be light
* Validators: Objects used by the controllers to ensure the data we get makes sense, for example we cannot schedule 
an interview in the past.
* Services: This is where most of the business logic happens, a controller may call one or more services
* DAO (Data Access Object): This is where the access to the database occurs. A service may call one or more DAOs

In general, the calls go Controller -> Service -> DAO. We do not want calls Controller -> Controller , Service->Service
DAO->DAO, etc. This is to keep things simple and avoid circular dependencies. 

We will use Log4j2 for logging and will log things to /tmp/LocoServiceYYYYMMDD.log so that the log rotates per day. 

An interceptor for AuthN/AuthZ is required before we hit the controllers. We can use a Spring security filter for this.

There are some rules to consider when interviewer. The main interviewer (it does not apply to the shadow), cannot 
be at a lower level than the candidate. For example an interviewer who is Level 5 cannot interview a candidate 
who is Level 6. They can only interview candidates who are same level or less.

Feedback is expected to be provided within 24hours after the interview. If that is not done within that time then 
it is considered to be late. 

A debrief is expected to be completed within 7 days of the last interview the candidate had. If that is not done then, 
it is considered late.

## LocoHiringJavaClient

This is probably the simplest thing to do. 

LocoHiringService must produce two maven artifacts: One for the service itself and one for the openapi spec. The idea 
is to write the spec first, and from that produce the service and the client. 

LocoHiringJavaClient takes a dependency on the openapi spec maven artifact and uses it to generate a http client 
capable of interacting with LocoHiringService.

Simple :) 

## LocoHiringWeb

This will use the previously generated LocoHiringJavaClient plus a SpringBoot with Thymeleaf for the frontend. 

The web is kept simple on purpose, no single page application, no react framework. We will use bootstrap for the 
frontend so that we produce a nice website. 

There are essentially three experiences

1. Global Admin
2. Recruiter
3. Interviewer

The global admin can do anything. As simple as that. They get to see the experience of recruiters and interviewers, 
both of them

Interviewers: Their landing page shows the following
    * Upcoming interviews
    * Pending interview feedback
    * Upcoming debriefs

Interviewers also have a section to manage their calendar where they can see what are the availability blocks they 
want to reserve for interviews, they can also see whether there is an interview associated with any of the timeslots 
they have provided. Interviewers can add new time slots for interviews. This can be done as a one-off operation, for 
example specify that this Thursday they are available to interview from 1 to 2pm or as a recurring one, for example 
saying they are available to interview Mondays 1pm to 3pm every week.      
     
Recruiter: Their landing page is a list of all the candidates they own. Candidates might have already gone through 
a debrief. Recruiters need to know whether the candidate needs to be contacted for feeback and whether we are late 
for contacting them. For example if a candidate has gone through an interview 2 days ago, we will need to know whether 
that interview has its feedback or not, etc. 

Recruiters can also see a list of all the available funnels, they can also create funnels, register new candidates, 
register new job families, etc. 

A large part of the recruiter jobs is to figure out who can interview candidates. Once a recruiter has locked a time 
with a candidate, it would be very useful if they could know quickly whether there is an available interviewer for 
that time slot. 

## Developer experience

It must be simple to develop locally. To do that we will use containers for everything: one for PostgreSQL, one 
for the LocoHiringService and one for the LocoHiringWeb, there will be a docker-compose.yml file at the top 
directory that will allow us to build and startup each of those three containers. 

The containers running java code (LocoHiringService and LocoHiringWeb) will expose ports 8080/5080 and 8081/5081 for 
HTTP Port and for remote java debugging. 

There will also be a parent maven file in the top directory (alongside with the docker-compose.yml) so that developers 
can load all the projects at once in the IDE and compile them with a single command. 

All containers receive a TZ env var that sets the system timestamp to Australia/Sydney.
